# v0.1.10 — oprava průběhu nad hotovými dávkami

Živé ověření v0.1.9 odhalilo dvě chyby nového průběhového okna. Hotový index zbytečně procházel celý korpus a při přeskakování hotových dávek zadržoval SQL rezervaci úlohy. Heartbeat a stavové čtení pak mohly čekat a úloha vypršela. Přehled souborů navíc v Azure používal pomalý plán vnořených outer joinů.

- Úplný index nyní skončí bez inicializace provideru a bez průchodu dávkami; neprovádí se žádná embeddingová inference.
- Přeskočené hotové dávky uvolňují transakci, aby mohl pokračovat heartbeat, zastavení a čtení průběhu. Regrese používá druhou skutečnou SQL session s omezeným lock timeoutem.
- Přehled spojuje tři dávková čtení a používá již ověřený scoped INNER HASH JOIN pouze mezi chunky a vektory. Tenantové filtry i ověření revizí zůstávají. Read-only důkaz na skutečném Azure: stejných 431 souborů / 9 372 platných chunků, **14,201 s → 0,128 s**.

Nativní Azure vytvoření/backfill/resume bylo ověřeno s JHU Nomic768 na třech vlastních syntetických chunkech v odděleném QA tenantu. První dávka uložila 1 chunk, pokračování pouze zbývající 2, opakování 0; výchozí index zůstal stejný a vlastní QA tabulka/řádky byly odstraněny. Nejde o nový přepočet aplikačního korpusu.

Výchozí celé sady v0.1.9 prošly 755/23 a čistý JHU 561/152; cílené regrese hotfixu nad SQLite i lokálním SQL a skutečný native/query-plan důkaz jsou samostatné navazující kontroly. Publikované tagy v0.1.9 se nepřepisují. Backend/helper/frontendy a zdrojová publikace zůstávají oddělené operace, kapacity se nenavyšují.
